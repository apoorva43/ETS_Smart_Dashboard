PISA Data Dashboard

Data Product Handoff Guide

Overview

Educational assessment data is frequently reported as static average scores, omitting crucial context and leading policymakers to attribute performance disparities to demographic groups rather than systemic inequities. To address this, we developed an interactive data product for the Educational Testing Service (ETS) that visualizes full score distributions and contextual variables using Programme for International Student Assessment (PISA) data.

The dashboard draws on student records from the 2015, 2018, and 2022 PISA cycles. Rather than reporting country averages alone, it surfaces the full score distribution, broken down by percentile, socioeconomic background, immigration status, school type, and location. A Parquet and DuckDB backend keeps query times low even at this scale, by pushing filters and aggregations down to the data layer before results reach the application.

The tool offers two modes: an open Explore view for analysts who want to slice the data themselves, and a guided Story mode that walks policymakers through key patterns with contextual framing. Sampling weights and plausible values are applied throughout, following PISA's methodology. The goal is to make it easier to ask more specific questions, not just how a country scores on average, but how different groups of students are distributed across the full range of performance.

Environment setup

You will need Conda (Miniforge or Anaconda) and roughly 6-7 GB of free disk space for raw data and processed Parquet files.

# Clone the repository
git clone https://github.com/apoorva43/ETS_Smart_Dashboard
cd ETS_Smart_Dashboard

# Set up the environment
conda env create -f environment.yml
conda activate ets_capstone
pip install -e .

# Run the data pipeline
make data
Note

See the Data pipeline section below for details on what each step does and how long each step takes. The raw PISA data files are not committed to the repo, they are downloaded as part of the data pipeline. Steps 1-3 download ~3-4 GB data and take around 15-20 minutes. Steps 6 and 7 (precomputations) are compute intenstive and take around 5-10 minutes.

Keeping dependencies in sync

The conda environment and the Posit deployment use separate dependency files. When you add a package, update both:

  • environment.yml - for local development via conda
  • requirements.txt - for Posit Cloud, which uses pip and reads this file on deploy

Running locally

PYTHONPATH=. streamlit run app.py

The app opens at http://localhost:8501. On startup it loads three small pre-aggregated files - country metadata for the sidebar, precomputed KDE and weighted percentile stats, and the Standard Error lookup. Each of these is cached with @st.cache_data for the session. Chart data is fetched on demand via DuckDB queries against pisa_all.parquet, loading only the columns and rows each chart needs.

PYTHONPATH=. ensures src/ is importable without installing the package each time. If your IDE already manages PYTHONPATH, you can omit it.

Deployment on Posit Cloud & S3

Posit Cloud

Posit is connected to the GitHub repo and auto-deploys on push to the dev branch. Dependencies are read from requirements.txt. Trigger a manual redeploy from the Posit dashboard if the auto-deploy does not fire.

The S3 bucket URL is set in two places, we need to update both when it changes (needs to be changed before 10 August, 2026):

  • src/data_loader.py - same constant used in the fallback fetch functions

Data pipeline

Everything runs through src/build_data.py, a Click CLI orchestrated by the Makefile. The command make data executes all seven steps in dependency order. Make only re-runs a step if its output file is missing or its inputs have changed.

1
Download the data

Pulls the student and school questionnaire zip archives from OECD URLs defined in src/data_loader.py. It includes the 2015, 2018, and 2022 PISA cycles.

2
Unzip the data

Unzips the downloaded PISA archive into its parent directory.

3
Convert to Parquet

Merges student and school files on the school identifier (CNTSCHID), selects the 133 relevant columns (30 plausible values, sampling and replicate weights, equity context variables), and writes a per-year Parquet file to data/processed/pisa_YYYY.parquet.

4
Merge cycles

Concatenates the three per-year Parquet files into pisa_all.parquet with a YEAR column added. This is the file all runtime chart queries hit via DuckDB.

5
Country stats

Computes one summary row per country-year (weighted means, OECD membership flag) and writes pisa_country_stats.parquet. It's used only to populate the sidebar and is never passed to a chart function.

6
Precompute KDE + weighted percentiles

For every combination of country x year x subject x group (gender, immigration status, SES quartile, school type, school location), fits Gaussian KDE curves across all ten plausible values and computes weighted P10/P25/P50/P75/P90. Results are saved in pisa_precomputed.parquet so the density charts render from lookup rather than fitting KDEs at runtime. Run with python -W ignore to suppress scipy bandwidth warnings on small groups.

7
Standard errors + 95% CI

Computes Fay BRR standard errors and 95% confidence intervals for every country x year x subject combination and writes pisa_se_stats.parquet, indexed for O(1) lookup at render time. This replaces loading all 80 replicate weight columns per chart render.

Running individual steps

You can bypass Make and run any step directly through the CLI:

# Re-run only the SE computation
python src/build_data.py standarderror

# Re-run only precompute with a custom output path
python -W ignore src/build_data.py precompute \
    --out-path data/processed/pisa_precomputed_v2.parquet

Output files

All the parquet files are saved in data/processed/ and are mirrored to S3 for the deployed environment. Neither raw .sav files nor processed Parquet files are committed to the repo - the S3 fallback in data_loader.py handles this transparently on Posit.

File Role
pisa_YYYY.parquet Per-cycle intermediate files (133 columns). Input to Step 4 of the data pipeline. This file is neither read at runtime nor is it uploaded to S3.
pisa_all.parquet Combined multi-cycle file with a YEAR column. Every runtime chart query hits this via DuckDB, loading only the specific rows and columns requested.
pisa_country_stats.parquet One row per country-year: weighted means and OECD membership flag. This is loaded once on startup for the sidebar and is never passed to a chart function.
pisa_precomputed.parquet Serialised Gaussian KDE arrays and P10-P90 for every group combination. This eliminates all runtime KDE fitting for the density charts.
pisa_se_stats.parquet Fay BRR standard errors and 95% CIs, indexed by (CNT, YEAR, SUBJECT) for O(1) lookup.

Backend & caching

The backend is built around the principle of never loading more data than a single chart needs. Every chart calls fetch(countries, year, cols) in app.py, which wraps query_pisa() in src/data_loader.py. DuckDB reads only the requested columns and rows from pisa_all.parquet - the full 1.7-million-row dataset is never loaded into memory.

Arguments to fetch() are typed as tuples rather than lists because @st.cache_data requires hashable arguments. The cache has a one-hour TTL.

# Fetch math PVs + weight for Canada, 2022
pv_cols   = tuple(f"PV{i}MATH" for i in range(1, 11))
base_cols = ("CNT", "W_FSTUWT", "ESCS", "IMMIG")

df = fetch(
    countries=("CAN",),
    year=2022,
    cols=base_cols + pv_cols,
)

Two-layer cache

  • Streamlit @st.cache_data - in-memory DataFrame cache keyed by (countries, year, cols) tuples with ttl=3600.
  • Precomputed Parquet artefacts - pisa_precomputed.parquet removes all runtime KDE fitting; pisa_se_stats.parquet removes loading 80 replicate weight columns per render. Computed once in the pipeline, read as O(1) lookups at runtime.

S3 fallback

get_meta(), get_precomputed(), and get_se_lookup() each try the local data/processed/ path first. If the file isn't there (the normal case on Posit, since processed files aren't committed), they fall back to S3_BASE_URL.

Frontend & charts

app.py has three main jobs: routing between the two modes, managing sidebar state, and calling the right chart function. The Data Story calls render_story_tab(), which walks through the four chapters in order. Explore calls render_chart(), which dispatches on chart_type.

Every chart function in src/plotting_plotly.py returns a go.Figure using _base_layout() for consistent styling - the same font, margins, legend position, and grid color across all chart types.

Precomputed vs. fallback code paths

Where a precomputed version of a chart exists (all density and trend charts), there are two code paths: a _precomputed variant that reads from the Parquet artefact, and a raw-data fallback for local development without the precomputed file. In production df_pre is always available, so the fallback is rarely used.

Callout system

The two-level callout system in the Data Story reflects the feedback we received - earlier versions showed colored boxes on every chapter, which felt overwhelming. The conventions are:

  • Blue - key findings from the data
  • Green - policy implications or actionable observations

Statistical methods

PISA's survey design imposes a few methodological constraints that every statistic in the dashboard must respect. These are required to produce estimates that generalize to national populations.

Plausible values

PISA gives each student ten plausible values per subject - multiple draws from the posterior distribution of their latent ability, designed to account for measurement uncertainty in a short adaptive assessment. Every score statistic in the dashboard (means, percentiles, standard errors) is computed by averaging across all ten plausible values per the PISA technical standards. No chart uses a single PV as a point estimate.

Sampling weights

W_FSTUWT is the final student sampling weight and must be applied to all estimates so results generalize to the national population rather than just the students who happened to be tested. Country sample sizes vary substantially - Canada contributes around 23,000 student records; the United States contributes about 4,500 - making correct weight application essential for any cross-country comparison.

Standard errors

Standard errors follow the Fay Balanced Repeated Replication method using the 80 replicate weights (W_FSTURWT1-W_FSTURWT80). Total variance combines sampling variance from the BRR replicates and imputation variance across the ten plausible values. The implementation lives in src/pisa_stats.py and was validated against values from the PISA data explorer; see notebooks/standard_error.ipynb.

Data suppression

Any subgroup breakdown with fewer than 30 valid observations is suppressed rather than shown. Applied in check_group_sizes() in app.py and inside the plotting functions themselves. Country-level figures with fewer than 100 valid rows after dropping missing weights are replaced with a warning panel.

Scope of the tool

Because PISA microdata cannot support causal claims, the dashboard is deliberately limited to descriptive and comparative reporting. It can show that two groups differ in score distributions, but it cannot determine why. Observed gaps may reflect socioeconomic sorting, language background, school resources, or regional policy context - factors that live outside the PISA dataset.

Adding a new PISA cycle

The pipeline is designed to make adding a new cycle straightforward. The following four things need to be updated:

Checklist

  1. Add the download URLs to PISA_URLS and PISA_SCHOOL_URLS in src/data_loader.py.
  2. Add the year to YEARS in the Makefile and to the --years argument in the merge step.
  3. Run make data to rebuild through Step 5, then run Steps 6 and 7 manually via the CLI.
  4. Upload the updated Parquet files to S3 so the deployed instance picks them up.

The one thing to check manually is whether the new cycle uses the same column names as the previous ones. The OECD occasionally renames questionnaire variables between administrations. Search src/data_loader.py for any year-specific column handling and add new renames there if needed before running the pipeline.

Adding a new chart type

Chart types are self-contained: a function in plotting_plotly.py, a name in CHART_TYPES, and a branch in render_chart(). The pattern is always the same:

# 1. Define the chart function in src/plotting_plotly.py
def plot_my_chart(df, subject, cnt, year=None) -> go.Figure:
    fig = go.Figure()
    # build traces 
    fig.update_layout(**_base_layout(title=f"My Chart | {SUBJECTS[subject]}"))
    return fig
# 2. Register the name in app.py
CHART_TYPES = [..., "My New Chart"]
# 3. Add a branch in render_chart()
elif chart_type == "My New Chart":
    df = fetch(
        tuple(selected_countries),
        selected_year,
        tuple(BASE_COLS + pv_cols),
    )
    fig = plot_my_chart(df, subject, primary_country, year=selected_year)
    render_plotly_chart_with_note(
        fig,
        note=get_chart_note("My New Chart"),
        key=f"my_chart_{widget_key}_{subject}_{selected_year}",
    )

Always use _base_layout() so the new chart inherits consistent styling. Add an entry to get_chart_note() for the text shown below the chart, and optionally to CHART_HELP_TEXT for the collapsible how-to-read expander.
